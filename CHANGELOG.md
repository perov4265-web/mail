# Почтовый сервер: пошагово

Инструкция для случая «свой домен, один-два ящика». Результат: рабочая
почта вида `info@example.com`, которая принимает и отправляет письма и
проходит проверки крупных почтовых служб.

Всюду вместо `example.com` подставляйте свой домен, вместо
`mail.example.com` — имя своего почтового сервера, вместо `203.0.113.10` —
IP своего VDS.

Времени на всё около двух часов, из них час уходит на ожидание DNS.

---

## Шаг 1. Два вопроса хостеру — до оплаты

От ответов зависит, будет ли работать отправка. Задайте их в предпродажный
чат прежде чем платить:

1. **Открыт ли исходящий порт 25?** Многие провайдеры закрывают его от
   спамеров. Без него сервер сможет принимать почту, но не отправит ни
   одного письма. Формулировка: «Планирую поднять корпоративный почтовый
   сервер для организации. Открыт ли исходящий 25-й порт или его открывают
   по запросу?»
2. **Прописываете ли PTR-запись?** Обратная зона для IP должна указывать
   на имя почтового сервера. Из панели домена туда не попасть — только
   через хостера. Без PTR письма отвергают почти все крупные службы.

Если на первый вопрос ответ «нет и не откроем» — берите другого хостера.
Обойти это нельзя.

---

## Шаг 2. Закажите VDS

**Тариф.** Для одного-двух ящиков хватает 2 ГБ памяти, 1–2 ядра, 20 ГБ
диска. Диск берите с запасом, если планируете хранить архив переписки.

**Система.** Debian 13 или 12 — самый лёгкий вариант, в простое занимает
около 200 МБ памяти. Ubuntu 22.04, 24.04 и 26.04 тоже поддерживаются.
Другие дистрибутивы не подойдут: установщик рассчитан на семейство Debian.

**Отдельный сервер.** Почтовый сервер занимает порты 25, 143, 465, 587 и
993, а на время выпуска сертификата — ещё и 80-й. Сайт на этой же машине
жить может, но веб-сервер придётся ненадолго останавливать при продлении
сертификата.

**Ключ SSH.** Если провайдер предлагает добавить ключ при создании —
добавьте, это надёжнее пароля:

```powershell
ssh-keygen -t ed25519
```

Содержимое `id_ed25519.pub` вставьте в панель провайдера.

## Шаг 3. Первый вход и обновление

```bash
ssh root@203.0.113.10
apt update && apt upgrade -y
```

**Если сервер не видит собственное имя.** Бывает, что `ping
mail.example.com` отвечает `No address associated with hostname`, хотя
через публичный резолвер имя разрешается:

```bash
dig +short mail.example.com @1.1.1.1
```

Это отрицательный кеш локального резолвера: он запомнил «такого имени
нет» ещё до того, как вы добавили запись. Лечится так:

```bash
resolvectl flush-caches 2>/dev/null || \
  printf 'nameserver 1.1.1.1\nnameserver 8.8.8.8\n' > /etc/resolv.conf
ping -c2 mail.example.com
```

Починить это нужно до первой отправки: почтовый сервер постоянно ходит в
DNS — проверяет SPF отправителей, ищет MX получателей, обращается к
чёрным спискам.

## Шаг 4. Если работаете через VNC-консоль

В веб-консоли и VNC буфер обмена обычно не работает, а дальше понадобится
перенести с сервера в панель DNS строку примерно на четыреста символов —
ключ DKIM. Перепечатывать вручную нельзя: ошибка в одном символе, и
подпись не сойдётся, а заметить это можно будет только по низкой оценке
проверяющего сервиса.

Заберите значение через браузер:

```bash
ufw allow 8080/tcp
cd /opt/mailserver/docker-data/dms/config/rspamd/dkim
python3 -m http.server 8080
```

Откройте `http://203.0.113.10:8080`, щёлкните по файлу, скопируйте
значение. Затем Ctrl+C и обязательно закройте порт:

```bash
ufw delete allow 8080/tcp
```

Установщик показывает эту же подсказку на шаге с DKIM.

**Про 22-й порт.** Если SSH выключен и вы работаете только через консоль
панели, открывать его в файрволе незачем — этот порт круглосуточно
перебирают боты. Установщик спрашивает об этом и по ответу «Через
VNC-консоль» 22-й порт не открывает.

---

## Шаг 5. Безопасность

Этот шаг нужен, **только если SSH включён**. При работе через VNC-консоль
порт закрыт снаружи, перебирать нечего, и работа под root вполне
обоснована — тогда переходите к шагу 6.

Если SSH открыт, пять минут здесь экономят много нервов: `root` —
единственное имя пользователя, известное ботам заведомо.

```bash
adduser admin
usermod -aG sudo admin
rsync --archive --chown=admin:admin ~/.ssh /home/admin
```

Проверьте вход в **новом окне терминала**, не закрывая текущее:

```bash
ssh admin@203.0.113.10
```

Работает — запретите вход по паролю в `/etc/ssh/sshd_config`:

```
PermitRootLogin prohibit-password
PasswordAuthentication no
```

```bash
systemctl restart ssh
```

## Шаг 6. Запись A — до установки

Сертификат Let's Encrypt выдаётся только тогда, когда имя уже указывает
на сервер. Поэтому запись A прописывается первой.

**Где.** В панели управления DNS вашего домена — там же, где заданы
записи сайта. Обычно это личный кабинет регистратора или хостинга сайта,
раздел «Настройка DNS» или «DNS-записи». Не на сервере и не в панели VDS.

| Тип | Имя | Значение |
|---|---|---|
| A | `mail.example.com.` | `203.0.113.10` |

Некоторые панели просят вводить короткое имя — просто `mail`. Посмотрите,
как записаны соседние строки, и сделайте так же. Записи сайта не трогайте.

Проверьте:

```bash
dig +short mail.example.com @1.1.1.1
```

Распространение занимает от 15 минут до двух часов. Пока запись не
разошлась, дальше не идите.

## Шаг 7. Установка

```bash
apt install -y git
git clone https://github.com/perov4265-web/mail.git
cd mail
chmod +x install.sh

# посмотреть план, ничего не меняя
./install.sh --dry-run

# установка
./install.sh
```

Без git можно скачать один файл — остальное в репозитории нужно только
для чтения:

```bash
apt install -y curl
curl -fsSLO https://raw.githubusercontent.com/perov4265-web/mail/main/install.sh
chmod +x install.sh
./install.sh
```

Мастер спросит домен, имя сервера, IP, ящики, режим приёма писем на
несуществующие адреса, часовой пояс и пароль, затем проверит систему и
установит всё сам, показывая ход работ.

Пароль ящика возьмите длинный и случайный: адрес будет открыт в интернет,
и его будут перебирать.

ClamAV включайте, только если на сервере больше 3 ГБ памяти. Для
нескольких ящиков антивирус избыточен, спам фильтрует Rspamd.

## Шаг 8. Остальные записи DNS

Установщик напечатает готовые значения. Добавьте их в панели DNS домена.

| Тип | Имя | Значение | Приоритет |
|---|---|---|---|
| MX | `example.com.` | `mail.example.com.` | 10 |
| TXT | `example.com.` | `v=spf1 mx ~all` | — |
| TXT | `_dmarc.example.com.` | `v=DMARC1; p=none; rua=mailto:postmaster@example.com` | — |
| TXT | `mail._domainkey.example.com.` | `v=DKIM1; k=rsa; p=` и длинная строка | — |

Ключ DKIM, если потерялся вывод:

```bash
cat /opt/mailserver/docker-data/dms/config/rspamd/dkim/*.public.key
```

**Если у домена уже есть запись MX** на другой почтовый сервис — удалите
её. Иначе письма пойдут по старому адресу.

**Три частые ошибки с DKIM.** При копировании из терминала в значение
попадают переносы строк — вставляйте одной сплошной строкой. Если панель
сама оборачивает значение в кавычки, свои добавлять не надо. И проверьте,
что сохранилось начало `v=DKIM1; k=rsa;` — некоторые панели обрезают
значение по первой точке с запятой.

Разбивка длинного значения на две части в кавычках — это нормально: так
DNS хранит строки длиннее 255 символов, при чтении они склеиваются.

**Что означают записи.** MX говорит, куда доставлять почту для домена.
SPF перечисляет, кому разрешено отправлять от вашего имени; `~all` —
мягкий режим: письма с чужих серверов помечаются подозрительными, но не
отвергаются. DKIM — подпись, подтверждающая, что письмо не изменено.
DMARC с политикой `p=none` пока только собирает отчёты; ужесточать до
`quarantine` стоит через месяц, когда убедитесь, что всё сходится.

## Шаг 9. Запросите PTR

Напишите в поддержку хостинга: «Прошу настроить PTR-запись для IP
`203.0.113.10` на имя `mail.example.com`». Обычно делают в течение часа.

```bash
dig +short -x 203.0.113.10 @1.1.1.1
```

Должно вернуться `mail.example.com.` с точкой на конце. Пусто — запись не
настроена. Строка вида `10-113-0-203.static.hoster.ru` — стоит значение
по умолчанию, его надо заменить.

Проверьте и обратное направление: `dig +short mail.example.com` должен
вернуть тот же IP. Почтовые службы сверяют обе стороны.

## Шаг 10. Проверка

**Все записи разом:**

```bash
dig +short MX example.com @1.1.1.1
dig +short TXT example.com @1.1.1.1
dig +short TXT _dmarc.example.com @1.1.1.1
dig +short TXT mail._domainkey.example.com @1.1.1.1
dig +short -x 203.0.113.10 @1.1.1.1
```

**Исходящий порт 25:**

```bash
timeout 8 bash -c 'exec 3<>/dev/tcp/gmail-smtp-in.l.google.com/25' \
  && echo "открыт" || echo "закрыт"
```

**Приём.** Отправьте письмо с любого своего ящика на `info@example.com`,
а вторым — на выдуманный адрес того же домена, если включали приём писем
на несуществующие адреса. Оба должны прийти в главный ящик:

```bash
find /opt/mailserver/docker-data/dms/mail-data -type d -name new
cd /opt/mailserver && docker compose logs --tail 30 | grep -i "status=sent"
```

Каталог ящика создаётся при первом доставленном письме, а не при создании
ящика, — до первого письма его не будет.

**Отправка и репутация.** Откройте mail-tester.com, скопируйте выданный
адрес, отправьте на него письмо из почтовой программы, вернитесь на сайт
за оценкой.

**Нужно 9 из 10 и выше.** Что чаще всего снимает баллы:

| Проблема | Решение |
|---|---|
| нет PTR | шаг 9 |
| DKIM не сходится | значение скопировано не целиком |
| IP в чёрном списке | multirbl.valli.org, заявка на исключение |

## Шаг 11. Прогрев

Новый сервер — чистый IP без репутации. Резкий старт почтовые службы
принимают за спам-атаку.

| Период | Писем в день |
|---|---|
| дни 1–3 | 10–15 |
| дни 4–7 | 20–30 |
| вторая неделя | 50 |
| третья неделя | 100 |
| дальше | 150–200 |

Отправляя первые письма, поставьте несколько своих адресов на разных
службах и посмотрите, куда они попали. Во «Входящие» у всех — можно
наращивать.

## Если что-то пошло не так

**Сервер не видит своё имя, но публичный резолвер видит** — отрицательный
кеш, шаг 3.

**Письма не уходят, в логе `Connection timed out`** — закрыт исходящий
порт 25, шаг 1.

**Контейнер перезапускается по кругу, в логе `at least one mail
account`** — не создан ни один ящик: docker-mailserver не запускает
Dovecot без ящиков и выключается через 120 секунд. Создайте ящик сразу
после запуска:

```bash
cd /opt/mailserver && docker compose up -d
docker exec -ti mailserver setup email add info@example.com
```

**Сертификат не выпустился** — запись A ещё не разошлась или занят 80-й
порт. Освободите порт и повторите:

```bash
docker run --rm -p 80:80 \
  -v /opt/mailserver/docker-data/certbot/certs/:/etc/letsencrypt/ \
  certbot/certbot certonly --standalone -d mail.example.com
```

**Почтовая программа ругается на сертификат** — в `compose.yaml` остался
`SSL_TYPE=self-signed`. Верните `letsencrypt` и выполните
`docker compose up -d`.

**Вход в ящик не проходит** — логин вводится целиком, с доменом:
`info@example.com`, а не `info`.

**Сообщения ядра сыплются поверх экрана в консоли** — это журнал ufw:

```bash
dmesg -n 1
ufw logging off
```
