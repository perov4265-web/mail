# Как пользоваться почтой

Что делать после того, как сервер поднят и записи DNS прописаны: чем
читать письма, как заводить новые ящики и адреса, как не потерять почту.

Всюду вместо `example.com` подставляйте свой домен, вместо
`mail.example.com` — имя своего почтового сервера.

---

## Настройки для почтовой программы

Одни и те же для Thunderbird, Outlook, Apple Mail, почтовых приложений на
телефоне и любых других клиентов:

| Параметр | Значение |
|---|---|
| Входящая почта | IMAP, `mail.example.com`, порт **993**, SSL/TLS |
| Исходящая почта | SMTP, `mail.example.com`, порт **587**, STARTTLS |
| Имя пользователя | адрес целиком: `info@example.com` |
| Пароль | заданный при создании ящика |
| Аутентификация | обычный пароль |

Три вещи, на которых спотыкаются:

**Логин — это адрес целиком.** Не `info`, а `info@example.com`. Половина
обращений «не входит в почту» — про это.

**IMAP, а не POP3.** IMAP оставляет письма на сервере, и почта выглядит
одинаково на компьютере и на телефоне. POP3 скачивает письма и удаляет их
с сервера — со второго устройства вы их уже не увидите. POP3 на порту 995
тоже работает, но включать его без нужды не стоит.

**Порт 587 со STARTTLS, а не 465.** Порт 465 тоже открыт и работает, но
587 — стандартный порт отправки, и его реже режут в публичных сетях.

Если программа ругается на сертификат, значит на сервере остался
самоподписанный: в `compose.yaml` стоит `SSL_TYPE=self-signed`. Выпустите
сертификат Let's Encrypt и верните `SSL_TYPE=letsencrypt`.

## Веб-почта

Из коробки её нет: docker-mailserver — это почтовый сервер, а не
веб-интерфейс. Если нужен доступ через браузер, поставьте рядом отдельным
контейнером Roundcube или SnappyMail и укажите в нём тот же
`mail.example.com` с портами 993 и 587.

Учтите, что веб-почта займёт порт 80 или 443 и потребует своего
сертификата — на том же сервере это уже полноценный веб-сервер со всеми
вытекающими.

## Ящики и адреса

Все команды выполняются на сервере.

```bash
# список ящиков и их размер
docker exec -ti mailserver setup email list

# новый ящик — пароль спросит скрыто
docker exec -ti mailserver setup email add sales@example.com

# сменить пароль
docker exec -ti mailserver setup email update info@example.com

# удалить ящик вместе с письмами
docker exec -ti mailserver setup email del sales@example.com
```

**Псевдонимы** — это дополнительные адреса, которые ведут в существующий
ящик. Отдельного пароля и отдельной папки у них нет, письма падают в ящик
назначения.

```bash
# заводим адрес-псевдоним
docker exec -ti mailserver setup alias add director@example.com info@example.com

# смотрим все псевдонимы
docker exec -ti mailserver setup alias list

# убираем
docker exec -ti mailserver setup alias del director@example.com info@example.com
```

Псевдоним удобнее второго ящика, когда адрес нужен «для вида»: `sales@`,
`support@`, `press@` — все ведут в один ящик, а отвечать можно с любого из
них, если добавить их как дополнительные адреса отправителя в почтовой
программе.

## Письма на несуществующие адреса

Установщик спрашивает об этом при настройке. Правило выглядит как
псевдоним `@example.com` — то есть «весь домен» — и ведёт в главный ящик.

```bash
# включить: всё, что пришло на несуществующий адрес, падает в info@
docker exec -ti mailserver setup alias add @example.com info@example.com

# выключить: отправитель получит уведомление, что адреса нет
docker exec -ti mailserver setup alias del @example.com info@example.com
```

С включённым правилом не теряется ни одно письмо — ни с опечаткой в
адресе, ни на давно закрытый адрес. Плата за это — спам: рассылки
перебирают адреса по словарю, и весь этот мусор пойдёт в тот же ящик.
Решение обратимо, попробуйте оба варианта.

## Спам

Фильтрует Rspamd, он же подписывает исходящие письма ключом DKIM.
Подозрительные письма попадают в папку «Спам» (Junk), а явный мусор
отклоняется на входе.

Правило простое: **перекладывайте письма руками**. Ошибочно попавшее в
спам письмо перенесите во «Входящие», пропущенный спам — в «Спам».
Rspamd учится на этих перемещениях и через пару недель начинает попадать
заметно точнее.

Посмотреть, почему письмо сочли спамом, можно в его заголовках: строка
`X-Spamd-Result` содержит набор сработавших правил и итоговый балл.

## Что где лежит

```
/opt/mailserver/
├── compose.yaml                     настройки сервера
└── docker-data/
    ├── dms/config/                  ящики, псевдонимы, ключи DKIM
    ├── dms/mail-data/               сами письма
    ├── dms/mail-logs/               журналы
    └── certbot/certs/               сертификаты
```

Письма хранятся в формате Maildir: каждое письмо — отдельный файл. Это
удобно для резервного копирования и позволяет при необходимости достать
письмо обычными файловыми командами.

## Обслуживание

```bash
# что происходит прямо сейчас
cd /opt/mailserver && docker compose logs -f

# очередь неотправленных писем
docker exec mailserver postqueue -p

# попробовать отправить очередь немедленно
docker exec mailserver postqueue -f

# перезапуск
cd /opt/mailserver && docker compose restart

# обновление до свежей версии
cd /opt/mailserver && docker compose pull && docker compose up -d
```

Пустая очередь — всё отправлено. Письма со статусом `Connection timed
out` означают, что закрыт исходящий порт 25.

## Резервное копирование

Вся почта и настройки лежат в одном каталоге, поэтому копия делается
одной командой:

```bash
tar czf /root/mail-$(date +%F).tar.gz /opt/mailserver
```

Настройте перенос архивов на другую машину: копия, лежащая на том же
сервере, копией не является. Раз в неделю достаточно.

Восстановление: развернуть архив на новом сервере, поправить `hostname`
в `compose.yaml`, если имя изменилось, и запустить `docker compose up -d`.

## Что проверять время от времени

**Раз в месяц** — не попал ли IP в чёрные списки: multirbl.valli.org.
Попадание не катастрофа, но чем раньше заметите, тем проще исключиться.

**Раз в месяц** — свободное место: `df -h`. Почта растёт незаметно,
особенно с включённым приёмом писем на несуществующие адреса.

**Через месяц работы** — отчёты DMARC. Они приходят на
`postmaster@example.com` от крупных почтовых служб и показывают, сколько
писем от вашего имени прошло проверки. Если всё сходится, политику в
записи `_dmarc` можно ужесточить с `p=none` до `p=quarantine`.

**Сертификат** продлевается сам: задание в `/etc/cron.d/mailserver-cert`
проверяет срок раз в неделю, журнал в `/var/log/certbot-renew.log`.
Проверить дату окончания:

```bash
openssl x509 -enddate -noout \
  -in /opt/mailserver/docker-data/certbot/certs/live/mail.example.com/fullchain.pem
```

## Ограничения, о которых стоит знать

**Массовые рассылки.** Свой сервер не отменяет правил: репутация нового IP
нарабатывается неделями, и резкий старт воспринимается как спам-атака.
Наращивайте объём постепенно и следите за долей отбивок — выше 5% это
сигнал, что список адресов пора чистить.

**Один сервер — одна точка отказа.** Если машина выключится, входящие
письма не пропадут: отправляющие серверы будут повторять попытки от
нескольких часов до нескольких суток. Но читать и отправлять вы в это
время не сможете.

**Правовая рамка рассылок.** Информационное письмо и приглашение к
сотрудничеству рекламой не являются и согласия адресата не требуют. Как
только в письме появляется продвижение товаров или услуг, начинает
действовать законодательство о рекламе: рассылка без согласия получателя
запрещена. Работающий способ отказаться от писем нужен в любом случае, и
отказ исполняется немедленно.
